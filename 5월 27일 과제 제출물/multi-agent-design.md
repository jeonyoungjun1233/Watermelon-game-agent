# 멀티에이전트 작업 설계안

## 1. 설계 목적

이 문서는 `괴짜 개발자 콩쌤 수박게임` 프로젝트의 게임 코드를 수정하지 않고, 과제 제출용 멀티에이전트 작업 구조를 설명하기 위해 작성했다.

기존 설계 문서는 5개 에이전트와 멀티에이전트 패턴을 자세하게 정리했다는 장점이 있었다. 이번 수정에서는 그 장점을 유지하면서, 실제 코드 `week11-suika-agent/my_agent.py`도 같은 5개 에이전트 구조를 가지도록 맞췄다.

## 2. 작업 제약

- 게임 실행 코드는 수정하지 않는다.
- `src`, `public`, `index.html`, `package.json`, `package-lock.json`은 읽기 전용으로만 확인한다.
- 산출물은 `multi-agent-project` 안에 모은다.
- 에이전트 간 정보 전달은 하나의 공유 상태 dict로 표현한다.

## 3. 단일 에이전트의 한계와 멀티에이전트가 필요한 이유

단순히 "게임 코드를 수정하지 않는다"는 조건만 보면 단일 에이전트로도 충분하다. 그래서 이 프로젝트에서 멀티에이전트가 필요한 이유는 수정 금지 자체가 아니라, 다음과 같은 작업 복합성 때문이다.

1. 컨텍스트 길이와 조건 누락 위험  
   과제 요구사항, 게임 프로젝트 구조, 제출 문서 형식, 수정 금지 파일 목록을 한 에이전트가 한 번에 처리하면 중요한 조건을 놓칠 수 있다. 역할을 나누면 각 에이전트가 맡은 범위를 더 명확하게 확인할 수 있다.

2. 책임 분리와 검증 관점 확보  
   문서를 작성한 에이전트가 바로 자신의 결과를 검토하면 빠진 설명이나 애매한 표현을 놓치기 쉽다. 작성, 사실 검증, 최종 형식 검토를 분리하면 제출물의 안정성이 높아진다.

## 4. 적용 패턴

### 4.1 기본 패턴: 계층형 + 순차형

프로젝트 매니저 에이전트가 전체 목표와 제약을 정리하고, 이후 에이전트가 순서대로 공유 상태를 이어받아 작업한다.

작업 흐름:

1. ProjectManagerAgent가 목표와 제약을 정리한다.
2. ContextAgent가 파일 구조와 준비 문서를 확인한다.
3. DocumentAgent가 설계 문서에 들어갈 핵심 내용을 만든다.
4. QAAgent가 사실 검증을 한다.
5. FinalReviewAgent가 제출 형식과 톤을 점검한다.

### 4.2 협력형 패턴

QA 단계에서 사용한다. 예를 들어 ContextAgent가 확인한 파일 목록과 DocumentAgent가 작성한 설명이 서로 맞는지 비교한다.

### 4.3 시장형 패턴

시장형 패턴은 "필요시 사용"이 아니라 아래 기준을 만족할 때만 사용한다.

- 문서 구조, 발표 방식, 구현 방식 후보가 2개 이상이다.
- 평가 기준이 명확하다. 예: 과제 적합성, 수정 금지 준수, 이해 쉬움, 구현 난이도.
- 후보를 비교하는 비용보다 더 나은 선택을 얻는 이득이 크다.

이번 Week 11 제출물은 구현해야 할 구조가 명확하므로 시장형 패턴을 기본으로 사용하지 않는다. 다만 발표용 요약본, 상세 보고서, 코드 중심 보고서처럼 제출 형식 후보가 여러 개 생기면 시장형 패턴으로 비교할 수 있다.

## 5. 공유 상태 dict 설계

`my_agent.py`의 모든 에이전트는 `run(self, state)` 메서드를 가진다. `state`는 하나의 dict이며 각 에이전트가 필요한 값을 읽고 새 값을 추가한다.

주요 키:

- `goal`: 이번 작업의 목표
- `constraints`: 수정 금지와 제출 범위 같은 제약
- `agents`: 실행되는 에이전트 목록
- `prepared_files`: `AGENTS.md`, `GEMINI.md`, `context.md`, `todo.md` 존재 여부
- `inventory`: 게임 프로젝트를 읽기 전용으로 확인한 결과
- `multi_agent_reason`: 멀티에이전트가 필요한 이유
- `pattern_policy`: 적용 패턴과 시장형 패턴 사용 기준
- `role_split`: QA와 최종 리뷰의 역할 차이
- `qa_result`: 사실 검증 결과
- `final_review`: 형식과 톤 검토 결과
- `handoffs`: 에이전트 간 인수인계 기록

## 6. 5개 에이전트 역할

### 6.1 ProjectManagerAgent

역할:

- 전체 목표를 정리한다.
- 작업 제약을 state에 기록한다.
- 실행할 에이전트 목록을 만든다.

산출물:

- 작업 목표
- 제약 조건
- 에이전트 실행 목록

### 6.2 ContextAgent

역할:

- 준비 문서가 있는지 확인한다.
- 게임 프로젝트 구조를 읽기 전용으로 확인한다.
- 게임 코드와 제출 문서 영역을 구분한다.

산출물:

- 준비 파일 확인 결과
- 게임 프로젝트 주요 파일 목록
- 이미지, 미디어, 함수, 의존성 요약

### 6.3 DocumentAgent

역할:

- 설계 문서에 들어갈 핵심 설명을 만든다.
- 멀티에이전트가 필요한 이유를 단일 에이전트의 한계와 연결해 정리한다.
- QA와 최종 리뷰 역할을 분리해서 기록한다.
- 시장형 패턴 사용 기준을 정리한다.

산출물:

- 멀티에이전트 필요 이유
- 패턴 사용 정책
- 역할 분리 설명
- 제출 보고서 섹션 구성

### 6.4 QAAgent

역할:

- 사실 검증을 담당한다.
- 준비 파일이 있는지 확인한다.
- 필수 state 키가 모두 채워졌는지 확인한다.
- 게임 코드가 수정되지 않았다는 조건을 확인한다.

QAAgent는 문장의 톤이나 발표용 표현보다 사실 여부를 우선한다.

산출물:

- 준비 파일 검증 결과
- 필수 항목 누락 여부
- 수정 금지 조건 확인 결과

### 6.5 FinalReviewAgent

역할:

- 형식과 톤 검토를 담당한다.
- 제출 보고서가 읽기 쉬운 순서인지 확인한다.
- 최종 제출 가능 여부를 판단한다.

FinalReviewAgent는 QAAgent처럼 파일 존재 여부를 다시 깊게 검사하기보다, QA 결과를 바탕으로 제출물의 흐름, 표현, 마무리를 확인한다.

산출물:

- 최종 승인 여부
- 제출 형식
- 문서 톤
- 최종 요약 메시지

## 7. QA와 최종 리뷰의 차이

QAAgent와 FinalReviewAgent는 모두 검토 역할이지만 기준이 다르다.

- QAAgent = 사실 검증  
  파일이 존재하는지, 요구사항이 빠지지 않았는지, 게임 코드 수정 금지 조건을 지켰는지 확인한다.

- FinalReviewAgent = 형식·톤 검토  
  제출 문서가 자연스럽게 읽히는지, 설명 순서가 좋은지, 과제 제출용 문장으로 정리됐는지 확인한다.

이렇게 나누면 "맞는 내용인가?"와 "제출하기 좋은 형태인가?"를 따로 점검할 수 있다.

## 8. 핸드오프 예시

```text
ProjectManagerAgent -> ContextAgent
완료: 목표, 제약, 에이전트 목록 기록
다음 작업: 프로젝트 구조와 수정 금지 파일 확인

ContextAgent -> DocumentAgent
완료: 준비 파일과 게임 구조 확인
다음 작업: 설계 문서와 제출 보고서 초안 작성

DocumentAgent -> QAAgent
완료: 멀티에이전트 필요 이유, 역할 분리, 시장형 기준 작성
다음 작업: 사실 검증

QAAgent -> FinalReviewAgent
완료: 파일 존재와 요구사항 충족 여부 확인
다음 작업: 형식과 톤 점검
```

## 10. 최종 판단

이번 작업은 게임 기능 개발이 아니라, 게임 프로젝트를 주제로 한 멀티에이전트 과제 제출물 정리 작업이다. 따라서 게임 코드를 직접 수정하는 방식은 적절하지 않다.

대신 5개 에이전트를 실제 코드 구조로 구현하고, 하나의 공유 상태 dict를 통해 에이전트 간 핸드오프를 보여 주는 방식이 과제 피드백에 더 직접적으로 대응한다.
